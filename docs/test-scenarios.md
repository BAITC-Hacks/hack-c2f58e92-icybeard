# Чистый стенд, тестовые данные и сценарии проверки

Для кого: тот, кто поднимает стенд на своей машине (Windows + Docker Desktop) и проходит продукт руками перед защитой
и перед внедрением. Упор — на цепочку «врач ↔ гражданин ↔ принимающая больница». Всё ниже сверено с кодом
на 01.10.2026; где описание опирается на чтение кода, а не на прогон, это сказано.

Содержание: 1 — переустановка с нуля · 2 — пользователи · 3 — тестовые данные · 4 — сценарии · 5 — что найдено
при ревью (критичное для внедрения, логические дыры, расхождения с документами).

## 1. Переустановка с нуля (Windows, PowerShell, из корня репозитория)

`make` на Windows не работает (цели `data`, `train`, `publish` зовут `ml/.venv/bin/python`, а `Makefile` жёстко
подключает `infra/deploy/targets/*.env`), поэтому всё — через `docker compose` напрямую. Все команды одной формы:

```powershell
$dc = "docker compose --env-file .env -f infra/docker-compose.yml"
```

### 1.1 Снести

```powershell
# контейнеры и ВСЕ тома (Postgres: журнал, аудит, аккаунты, опубликованные витрины; ClickHouse; MinIO; MLflow; данные скрайба)
docker compose --env-file .env -f infra/docker-compose.yml --profile app --profile pipeline --profile ollama down -v
# витрины, модели и справочники — пересоберёт конвейер (bronze/silver/quarantine/manifests стирать ТОЛЬКО все вместе —
# иначе повторная загрузка задвоит данные, файлы silver именуются по batch_id)
Remove-Item -Recurse -Force .\lakehouse
# карточки моделей и контракты конвейер перезаписывает — вернуть версию из git
git checkout -- docs/model-cards contracts
# по желанию: кэш сборки Docker (по журналу разработки дорастал до 40 ГБ)
docker builder prune -f
```

Что **не** трогать: Ollama на хосте (`%USERPROFILE%\.ollama`). `DataSets\` (~113 ГБ сырых CSV) можно стереть, если
хотите малый стенд — см. §1.3: четыре набора по одной части скачиваются за минуты и весят сотни мегабайт.

Keycloak тома не имеет: при пересоздании контейнера realm импортируется из `infra/keycloak/darumen-realm.json`
заново — сменённые пароли, TOTP и созданные пользователи (в том числе из `seed_routes.py`) пропадают.

### 1.2 Настроить `.env`

```powershell
Copy-Item .env.example .env
```

Обязательных переменных нет (у всего есть значения по умолчанию), но для Docker-стенда на `:3000` поправьте две,
иначе ссылки из писем (приглашения, сброс пароля) ведут на `:5173`:

```
WEB_PUBLIC_ORIGIN=http://localhost:3000
DARUMEN_WEB_URL=http://localhost:3000/
```

LLM: либо Ollama на хосте (`ollama pull qwen3.8:27b`, затем `ollama create darumen-qwen3.8:27b -f infra/ollama/Modelfile`),
либо облачный провайдер только для «Вопросов к данным» (`INSIGHT_PROVIDER / INSIGHT_BASE_URL / INSIGHT_MODEL / INSIGHT_API_KEY`).
Скрайб и загрузка данных в compose зашиты на Ollama: без неё черновики строятся по правилам, это не ошибка.
`DEEPSEEK_API_KEY` из `.env` в контейнеры не передаётся. На слабой машине `WHISPER_MODEL=small`.

### 1.3 Поднять инфраструктуру и прогнать данные

Малый стенд (достаточно для всех сценариев ниже; скрипт теперь работает и на Windows, нужен `curl` — есть в Windows 10+):

```powershell
Remove-Item -Recurse -Force .\DataSets -ErrorAction SilentlyContinue
python scripts\download_datasets.py referrals waiting refusals treated_count --max-parts 1
```

`--max-parts 1` берёт первую часть каждого набора (сотни МБ вместо ~113 ГБ): регионов и очередей меньше, но карта,
рабочий список, маршрут, симулятор и консоль оператора работают. Полный набор — та же команда без `--max-parts`
(в WSL, несколько часов).

```powershell
# Postgres, ClickHouse, Kafka, Schema Registry, Keycloak, Mailpit, MLflow …
docker compose --env-file .env -f infra/docker-compose.yml up -d

# конвейер: intake → refdata → gold → train → publish (DataSets и lakehouse монтируются с хоста). 10–40 минут.
docker compose --env-file .env -f infra/docker-compose.yml --profile pipeline run --rm --build pipeline
```

Конвейер **не** запускает `evaluate` (сравнение с baseline) — это отдельно, если нужно обновить `/quality`:

```powershell
docker compose --env-file .env -f infra/docker-compose.yml --profile pipeline run --rm --entrypoint python pipeline -m darumen.models.evaluate --lakehouse /lakehouse
```

### 1.4 Поднять приложение

```powershell
docker compose --env-file .env -f infra/docker-compose.yml --profile app up -d --build
```

Проверка, что всё живо: веб http://localhost:3000 · API http://localhost:8000/scalar · Keycloak http://localhost:8080
(консоль admin/admin) · почта http://localhost:8025 (Mailpit — сюда падают все письма) · загрузка данных
http://localhost:8020/docs · MLflow http://localhost:5000. `GET http://localhost:8000/health` отвечает `Healthy` даже
при упавшем Postgres (проверок внутри нет — см. §5.2), так что ориентируйтесь на `docker compose ps` и логи:

```powershell
docker compose --env-file .env -f infra/docker-compose.yml --profile app logs -f --tail=100 api models web
```

Пересборка одного сервиса после правок кода: `… --profile app up -d --build web` (или `api`, `models`, `scribe`, `intake`).

### 1.5 Лёгкая переустановка (витрины целы, нужно только обнулить журнал и аккаунты)

```powershell
docker compose --env-file .env -f infra/docker-compose.yml --profile app down -v
docker compose --env-file .env -f infra/docker-compose.yml up -d
docker compose --env-file .env -f infra/docker-compose.yml --profile pipeline run --rm --entrypoint python pipeline -m darumen.lakehouse publish --lakehouse /lakehouse
docker compose --env-file .env -f infra/docker-compose.yml --profile app up -d --build
```

Если нужно обнулить **только маршруты** (журнал переводов), а аккаунты и аудит оставить — `scripts/dev/reset-routes.sql` (§3).

### 1.6 Тесты

`test.cmd` — все тесты (.NET, Python, веб) в контейнере `mcr.microsoft.com/dotnet/sdk:10.0`; внутри нужен интернет (uv, Node).
Только веб: `cd apps\web; npm run test -- --run; npm run lint` (lint = `vue-tsc`).

## 3. Тестовые данные

Что откуда берётся, чтобы не искать «пропавших» пациентов:

- **Очереди, ожидание, отказы, индекс, аномалии, симулятор** — реальные агрегаты из `DataSets` (I квартал 2025).
- **Пациенты рабочего списка** — синтетические, по 6 на очередь (организация × профиль), ≤ 60 на регион; реф вида
  `SYN-75-028B-381-03` (регион-организация-профиль-номер). Они не хранятся в базе, а пересчитываются от среза витрины —
  поэтому после пересборки витрин состав может измениться.
- **Персона гражданина** — одна из первых **пяти** строк рабочего списка региона с флагом «ждёт > 30 дней» или
  «есть быстрее»; какая именно — хэш ИИН. Поэтому у одного гражданина всегда один и тот же пациент, а гражданин
  с другим ИИН получает другую (или ту же) из пяти персон. На экране гражданина реф не показан — виден в
  Network (`GET /api/v1/route/me` → `patientRef`) или по строке с флагом сигнала в рабочем списке врача.
- **Чек-лист анализов и история госпитализаций у гражданина** — тоже генерируются хэшем (не данные), «7 из 10 просрочены» — артефакт генерации.
- **Журнал маршрутов** (переводы, согласия, подтверждения, выписки) — единственное, что живёт в Postgres (`journal.decisions`,
  `subject = route`). Чистый стенд = пустой журнал, то есть ни одного перевода — цепочку надо «разогнать».

### 3.1 Скрипт: пять маршрутов в разных стадиях

```powershell
python scripts\dev\seed_routes.py
# адреса по умолчанию: API http://localhost:8000, Keycloak http://localhost:8080 (admin:admin)
```

Что делает (только через публичный API и Keycloak Admin API, в базу напрямую не пишет, поэтому аудит, уведомления и
правила состояний отрабатывают по-настоящему):

1. Берёт `citizen1` и создаёт `citizen2…citizenN` с ИИН `000000000002…`, пока не наберёт **пять разных** персон
   (дубликаты удаляет). Для больниц, у которых нет демо-врача, создаёт `doctor_<код МО>` (пароль `darumen`).
2. Доводит маршруты до стадий:
   1. сигнал гражданина «рассмотрите больницу быстрее» — ждёт врача;
   2. врач предложил перевод — ждём согласия;
   3. пациент согласился — ждём подтверждения принимающей (с пометкой «тяжёлый случай»);
   4. принимающая подтвердила **на сегодня** — можно сразу отметить госпитализацию и выписать;
   5. принимающая отказала — пациент остался в своей очереди.
3. Печатает: кто есть кто (логин гражданина → реф → больница пациента → куда переводят → врачи обеих сторон).

Повторный запуск маршруты с решениями пропускает. Полный сброс маршрутов:

```powershell
docker compose --env-file .env -f infra/docker-compose.yml cp scripts/dev/reset-routes.sql postgres:/tmp/r.sql
docker compose --env-file .env -f infra/docker-compose.yml exec postgres psql -U darumen -d darumen -f /tmp/r.sql
```

Ограничения, которые скрипт обойти не может (они в самой системе, см. §5.3):
- персон на регион только пять, поэтому больше пяти «живых» граждан в одном регионе не бывает;
- больница пациента у `citizen1` зависит от витрины — не обязательно 028B. Если нужен именно `doctor1`, смотрите
  в выводе скрипта, какой врач отвечает за больницу пациента, и входите им;
- «неявку» нельзя отметить в день даты, «дата прошла» появляется через 4 дня — на свежем стенде эти ветки
  проверяются только по тестам (`tests/Darumen.Tests/RouteProgressTests.cs`) или подменой даты в БД.

### 3.2 Остальное тестовое

- Согласие на запись приёма (скрайб): `scripts/dev/scribe-consent.sql` (аргумент `-v ref=SYN-…`).
- Демо-рецепты: `scripts/demo_rx.sql`.
- Файл с незнакомой структурой для консоли оператора: любой CSV с произвольными колонками — появится карточка
  «Файлы с незнакомой структурой» с черновиком описания.

## 4. Сценарии

Формат: кто → где → что сделать → что должно произойти. «Баг», если результат отличается. Сценарии С1–С4 — главная
цепочка, проходить подряд после `seed_routes.py` (или вручную с чистого журнала: тогда в С1 гражданин сам создаёт сигнал,
а дальше по шагам).

### С1. Гражданин видит свой путь и может попросить быстрее

1. Войти `citizen1` → открывается «Мой путь».
   - Ожидаемо: больница, профиль, этап («ожидает» / «вызов на госпитализацию»), сколько ждёт, прогноз ожидания
     с подписью, откуда он (модель / медиана), шкала этапов, чек-лист обследований, блок «Где быстрее» с 1–3
     больницами (p90 ожидания, риск отказа, расстояние).
   - Если «Где быстрее» пуст — сервис моделей не поднят (`docker compose ps models`), это не баг веба.
2. В «Где быстрее» нажать «Попросить рассмотреть», комментарий по желанию.
   - Ожидаемо: карточка «запрос отправлен, ждёт ответа врача»; повторная кнопка на ту же больницу недоступна.
3. Колокольчик гражданина: событий пока нет (ответит врач).
4. Прямая ссылка на чужой реф (`/doctor/patients/SYN-…`) под гражданином → «Нет доступа» с объяснением, кто выдаёт доступ.

### С2. Врач работает со списком и принимает решение

1. Войти врачом больницы пациента (`doctor1` для 028B; иначе — врач из вывода скрипта) → `/doctor/worklist`.
   - Ожидаемо: ≤ 60 пациентов региона, отсортированы по приоритету **0…10** (7–10 красный, 4–6 жёлтый, 0–3 зелёный),
     подсказка на кружке «8 из 10»; флаги: «ждёт > 30 дн.», «риск отказа», «есть быстрее», «сигнал пациента»;
     следующий шаг словами; фильтр «с сигналом пациента» оставляет строку из С1.
   - Приоритет **не** должен меняться от фильтров и региона (раньше красился относительно максимума списка — исправлено).
2. Открыть пациента из С1 → карточка маршрута.
   - Ожидаемо: панель врача — прогноз, риск отказа с объяснением факторов (SHAP), приоритет «n из 10», сигнал
     пациента с комментарием и пометкой «просил пациент» у нужной больницы в блоке альтернатив.
3. «Оставить» с причиной → статус «решение принято», сигнал закрыт; у гражданина в колокольчике «врач оставил, причина».
   Либо «Перевести» в больницу из альтернатив (при желании «Тяжёлый случай») с причиной.
   - Ожидаемо: 201, строка в рабочем списке — «ждём согласия», кнопка «Отменить перевод»; у гражданина карточка
     «Предложен перевод» с «Согласен / Отказаться / Больше не нужно» и уведомление «нужен ответ».
   - Без причины — 422 и подсветка поля. Повторный клик (двойной) не создаёт второй записи (Idempotency-Key).
4. Журнал решений `/doctor/decisions`: обе записи (рекомендация системы ↔ выбор врача, причина, время).

### С3. Согласие → подтверждение → госпитализация → выписка (полная цепочка)

Используйте маршрут из стадии 2 скрипта (или продолжение С2).

1. **Гражданин** → «Мой путь» → «Согласен».
   - Ожидаемо: карточка «ждём подтверждения больницы»; у врача-отправителя в колокольчике «пациент согласился».
2. **Принимающая** (`doctor2` для 22GN; иначе врач из вывода скрипта) → `/doctor/referrals/incoming`.
   - Ожидаемо: строка пациента; согласие «получено»; тег «тяжёлый» у маршрута стадии 3; кнопки
     «Подтвердить» / «Отказать». До согласия пациента кнопок нет, а подтверждение через API даёт 409.
3. «Подтвердить»: дата по умолчанию сегодня; попытка поставить вчера или +31 день → ошибка валидации (окно 0…30 дней).
   - Ожидаемо: статус «переведён, дата …»; у гражданина больница в шапке меняется на принимающую, остаётся только
     «Отказаться от госпитализации»; у отправителя пациент уходит из списка, в колокольчике «подтверждено»;
     у принимающей пациент появляется в рабочем списке с флагом «переведён к нам».
4. **Принимающая** → «Госпитализирован» (доступно только если дата = сегодня) → у гражданина «в больнице».
5. «Выписать» с текстом эпикриза (без текста — ошибка).
   - Ожидаемо: маршрут закрыт; гражданин видит все этапы пройденными, **текст эпикриза ему не показывается**;
     врач-отправитель получает эпикриз в колокольчик; главврач и аудитор видят записи в журнале/аудите.
6. После закрытия у гражданина нет действий. (Ограничение: сброс персоны не предусмотрен — гражданин привязан к
   закрытому маршруту; на стенде — `reset-routes.sql`.)

### С4. Альтернативные ветки

| Ветка | Кто и где | Ожидаемо |
|---|---|---|
| Пациент отказался от перевода | гражданин → «Отказаться» (с причиной) | маршрут «оставлен», больница пропадает из альтернатив, пока пациент сам её не попросит; отправитель получает уведомление |
| Больница отказала | принимающая → «Отказать» с причиной (стадия 5 скрипта) | пациент в своей очереди; эту больницу нельзя предложить снова (409 «уже отказала»); **отправителю уведомление не уходит, в списке он видит «решение принято»** — см. §5.3 F/H |
| Отмена перевода врачом | отправитель → «Отменить перевод» до подтверждения | «оставлен», гражданину уведомление |
| Перенос даты | принимающая → «Перенести» (причина, дата в окне 0…30 от сегодня) | гражданину новая дата; переносов можно сделать сколько угодно — §5.3 I |
| Неявка | принимающая → «Не явился» — только со **следующего** дня после даты | маршрут закрыт; пациент пропадает из всех списков, в исходную очередь не возвращается — §5.3 J |
| «Хочу остаться» | гражданин → «Хочу остаться в своей больнице» | у врача пропадает подсказка «предложить перевод»; перевести всё равно можно (так задумано) |
| Снятие с очереди | гражданин → «Больше не нужно / лечился в другом месте» | «запрошено снятие»; врач больницы пациента (после подтверждения — принимающей) закрывает маршрут с причиной |
| Дата прошла | дата + 4 дня без отметки | флаг у обеих сторон; уведомлений нет — §5.3 H |

### С5. Врач: ассистент направления, скрайб, памятка

1. `/doctor/referral` → регион, профиль, диагноз → список больниц с прогнозом p50/p90, риском отказа, объяснением;
   «Подтвердить выбор» пишет решение (рекомендация ↔ выбор) в журнал.
2. `/doctor/scribe`: выбрать пациента → «Запросить согласие» → согласие ставится SQL-скриптом (`scribe-consent.sql`,
   действует сегодня, на один приём) → запись → стенограмма → черновик заключения (секции) → правка → «Утвердить»
