### 1. Три найденных бага (S, по отдельности)

**1.1 Утечка региона в рабочем списке.**
Файл: `src/Darumen.Modules/Journal/JournalEndpoints.cs`, эндпоинт `/worklist`, сейчас:
```csharp
var region = regionKato ?? user.RegionKato ?? "75";
```
Query-параметр `regionKato` побеждает claim пользователя — можно подставить чужой регион. Исправить по образцу
`RouteEndpoints.ResolveAsync` (там уже правильно): регион берётся из `RegionAccess.RegionScope(user)`, параметр
запроса используется только если у пользователя нет ограничения (`regulator`/`admin` без региона). Тест: врач/org_admin
региона A не может получить `worklist?regionKato=<регион B>` — должен быть 403 или его же регион, не чужой.

**1.2 Слишком широкий скоуп рабочего списка врача.**
`docs/rbac.md`, строка `worklist.view`: у `doctor` сейчас `all`, у `org_admin` — `own`. Врач должен видеть только
пациентов своей организации. Изменить: `role_permissions` для `(doctor, worklist.view)` → scope `own`. Проверить
сиды в Keycloak-миграции и `apps/web/src/lib/permissions.ts` (`ROLE_PERMISSIONS.doctor['worklist.view']`) — привести
к `O` (own), это фронтовая копия матрицы, должна совпадать с БД. Тест: врач больницы А не видит пациентов больницы Б
в `/journal/worklist`.

**1.3 Закрытие аномалии не ограничено регулятором.**
Файл: `src/Darumen.Modules/Analytics/AnalyticsEndpoints.cs`, строка 38:
```csharp
private static readonly string[] AnomalyPermissions = [Permissions.GovMap, Permissions.OrgCabinet];
```
Это верно для *просмотра* (`GET /anomalies`), но `POST /anomalies/{id}/ack` (строка 83) использует тот же список —
закрыть сигнал может любой с `gov.map`/`org.cabinet`, не только регулятор. Разделить на два списка: `AnomalyViewPermissions`

если её ещё не внедрили — на сегодня достаточно ограничить `ack` только ролью `regulator` без региональной проверки).
Тест: `org_admin` с `gov.map` получает 403 на `POST /anomalies/{id}/ack`.

### 2. Согласие пациента на направление (M)

Сейчас: `POST /route/{patientRef}/redirect` (`RouteEndpoints.cs`, требует `Permissions.ReferralConfirm`) создаёт
решение о переносе сразу, без ответа пациента — `RouteRedirectRequestDto(ToMoCode, Reason)`. Пациент только видит
результат на маршруте (`RouteDto.Decisions`), согласия не спрашивают.

Станет:
- Новое поле в `RouteDecisionDto` (добавляющее, не ломает контракт): `PatientConsent` — `"pending" | "accepted" | "declined"`,
  по умолчанию `"pending"` для решений `Kind == Redirect`, для `Kind == Keep` не применяется (`null`).
- Новый эндпоинт `POST /route/{patientRef}/decisions/{decisionId}/consent` с телом `{ accepted: bool, reason?: string }`,
  доступен по `Permissions.RouteOwn` и только владельцу маршрута (как остальные citizen-эндпоинты в `RouteEndpoints.cs`).
  При `accepted: true` — стадия маршрута переходит в `RouteStages.Waitlisted`/следующую по `ToMoCode`; при `false` —
  решение помечается отклонённым, пациент остаётся в очереди исходной организации (аналог `keep`).
- `RouteDto.Doctor` (панель врача) получает пациента с `PatientConsent == "pending"` в отдельном срезе ворклиста —
  врач видит, что направление подано, но ещё не подтверждено пациентом.
- Миграция EF: новая колонка `patient_consent` в таблице решений (`journal.decisions` или её эквивалент) — новой,
  отдельной миграцией, без изменения существующих.
- Тест: `redirect` без ответа пациента не переводит стадию маршрута дальше `referral_issued`; `consent(accepted:false)`
  не создаёт запись в рабочем списке принимающей организации.

### 3. Клинический флаг тяжести случая (S/M)

Сейчас: `Worklist.cs` содержит только очередные флаги (`StuckOver30`, `RefusalRisk`, `FasterAlternative`, `PatientSignal`,
константы в `WorklistBuilder`, строки 64–70). Клинической тяжести нет.

Станет:
- Новая константа `ClinicalSeverity = "clinical_severity"` в том же классе (рядом с `PatientSignal`), не заменяет
  существующие, добавляется в `RiskFlags` независимо от очередных условий.
- Ставится врачом при вызове `redirect` — добавить необязательное поле `Severe: bool` в `RouteRedirectRequestDto`
  (добавляющее изменение контракта). Если `true` — флаг попадает в `WorklistItemDto.RiskFlags` принимающей организации.
- Тест: направление с `Severe: true` попадает в рабочий список принимающей организации с флагом `clinical_severity`
  независимо от `PRefusal`/`StuckOver30`.

### 4. Подтверждение приёма: разделение обычных и флагованных (L — самая тяжёлая задача P0)

Сейчас: `Permissions.ReferralConfirm` даёт право подтверждать/перенаправлять любому врачу с этим правом, нет
разделения на обычные и тяжёлые случаи по получателю.

Станет (минимальная версия на сегодня, **без создания новой роли в Keycloak** — это P2, задача 8):
- Обычные случаи (`RiskFlags` без `clinical_severity`) — подтверждает `org_admin` принимающей организации через
  существующий `Permissions.OrgCabinet`/`ReferralConfirm` (уже есть право `own` у `org_admin` на `referral.confirm`
  в текущей матрице rbac.md) — то есть технически ничего создавать не нужно, только зафиксировать в UI, что для
  обычных случаев подтверждает administrator организации, а не рядовой врач.
- Флагованные случаи (`clinical_severity` в `RiskFlags`) — новый эндпоинт или фильтр в `/journal/worklist?flag=clinical_severity`
  для принимающей организации, показывается только врачам с назначенным профилем/отделением (если поля отделения
  ещё нет — временно фильтровать по `ProfileCode`, полноценная привязка врача к отделению — задача 10).
- Тест: обычный случай не появляется в персональном "срочном" фильтре врача; флагованный появляется.

Если к вечеру L-задача не укладывается — можно сократить до фильтра `flag=clinical_severity` в существующем
worklist без отдельного адресного уведомления (задача 7 ниже) и доделать адресность после хакатона.

### Задача 4 — как решена архитектурная блокировка

Проблема из предыдущего статуса (принимающая организация не может открыть `/route/{patientRef}`, потому что
`mo_code` в самом рефе — это организация-отправитель) решена не переделкой `/route/*`, а отдельным путём, который
не зависит от `patientRef`-адресации:

- `GET /journal/referrals/incoming` (`JournalEndpoints.cs`) — входящие направления своей организации: те же
  строки `journal.decisions`, что видит `ListForOrganizationAsync` (уже умеет фильтровать по
  `chosen->>'moCode'` — это ровно организация-получатель), плюс отбор именно redirect (не сигналов, не самого
  согласия, не уже записанного подтверждения) и разбор `subjectId` через `RoutePatientRef` для имени и кода
  организации-отправителя. Доступ — тот же `worklist.view`, что и у `/journal/worklist` (own у врача/org_admin).
- `POST /journal/referrals/{decisionId}/confirm` — ещё одна запись в тот же journal.decisions
  (`ReferralConfirmation.cs`, новый файл, по образцу `RouteConsent.cs`): `chosen = {moCode, confirms: decisionId}`.
  Организацию, которая подтверждает, берём из claim `mo_code` актора, а не из scope разрешения — потому что у
  врача `referral.confirm` исторически `all` (может перенаправить куда угодно), но подтвердить приём он может
  только в свою собственную организацию. 409, если пациент ещё не согласился (`RouteConsent.Accepted`) или если
  направление уже подтверждено — это тот же human-in-the-loop принцип, что и в задаче 2, только с другой стороны
  решения.
- Тест: `RouteTests.Incoming_referral_requires_patient_consent_before_the_receiving_organization_can_confirm_it` —
  весь путь целиком: `/route/{patientRef}` даёт 403 принимающей стороне → направление видно в
  `/journal/referrals/incoming` → подтвердить нельзя, пока пациент не согласился (409) → после согласия —
  подтверждается (201) → повторно — 409 → организация-отправитель у себя это направление не видит.
- Веб: новая страница «Входящие направления» (`/doctor/referrals/incoming`, `IncomingReferralsView.vue` +
  `useIncomingReferrals.ts`) в меню «Пациенты» рядом с рабочим списком (та же `worklist.view`) — таблица
  пациент/отправитель/дата/согласие пациента/тяжесть/кнопка «Подтвердить приём» (задизейблена, пока
  `patientConsent !== 'accepted'`). У врача на странице маршрута (`RoutePatientView.vue`) появился чекбокс
  «Тяжёлый случай» при направлении — иначе `Severe` неоткуда было бы взяться из интерфейса вообще.

### Задача 7 — что на самом деле сделано

Полноценного push как не было, так и нет (сознательно, см. план — это P2, задача 13). Сделан именно тот минимум,

- Пока `pending` — вместо кнопки «Понятно» показываются «Согласен» / «Отказаться» (`POST /route/me/consent`),
  и банер не прячется, пока пациент не ответит (это и есть «уведомление, требующее действия», не просто плашка).

- Лента решений (`RouteFeed.vue`) у обеих сторон показывает статус согласия по каждому решению-редиректу;
  тяжесть (`Severe`) показывается **только врачу** — сознательно не показывается гражданину, чтобы не превращать

## Обновление статуса: задача 13 (колокольчик вместо push) и задача 11 (выписка/эпикриз) — реализованы

**Решение по задаче 13.** Вместо push-инфраструктуры (FCM/APNs) — внутрисистемные уведомления («колокольчик»).
Осознанно НЕ через Kafka и НЕ через WebSocket/SignalR:
- Прод-стенды (`infra/docker-compose.prod.yml`) работают в `Messaging Mode: local` (outbox в Postgres, без Kafka) —
  событийная шина через Kafka была бы недоступна именно там, где стоит реальный продукт.
- Ни один существующий экран системы (worklist, входящие направления, аудит, аналитика) не push-based — все читают
  `journal.decisions` по HTTP-запросу. WebSocket только ради колокольчика был бы нестыкующимся технологическим
  островком без реальной причины (задержка в 30–45 секунд не критична для уведомления о направлении пациента).
- Выбран лёгкий поллинг раз в 45 секунд с фронтенда, пока вкладка открыта (`useNotificationBell.ts`) — ощущение
  «живого» продукта без новой инфраструктуры.

**Архитектура хранения.** Единственное новое постоянное состояние — таблица `journal.notification_reads`
(actor, decision_id, kind, read_at), составной ключ (actor, decision_id, **kind**). Kind обязателен: у одного и того
же decisionId направления бывает несколько разных уведомлений по очереди (подтверждение, затем выписка) — без kind
отметка «прочитано» для одного события ложно закрывала бы и другое. Всё остальное («сколько входящих ждёт
подтверждения», сами тексты уведомлений) считается на лету из уже существующих данных — по аналогии с тем, как
устроены все остальные экраны системы (найдено при ревизии проекта до начала работы: ни один другой экран не имеет
своего кэша/materialized view поверх `journal.decisions`).

**Задача 11 (выписка)** реализована по образцу задачи 4 (`ReferralConfirmation`): новый `DischargeSummary.cs`,
эндпоинт `POST /journal/referrals/{decisionId}/discharge` (требует, чтобы приём уже был подтверждён — 409 иначе;
повторная выписка — тоже 409). Явка эпикриза видна направившей стороне через колокольчик (`UnreadDischarges`),
отдельно от уведомления о подтверждении (разные `kind`).

сигналы гражданина и подтверждения; при добавлении задачи 11 сразу же (не постфактум, как было с задачей 4) добавлено
исключение `DischargeSummary.Discharges(...) is not null` — проверено `grep` по всем использованиям
