# Вход через eGov mobile: что возможно, что сделано, что запрошено

Составлено 22 сентября 2026 по первоисточникам (ссылки ниже). Документ отвечает на вопрос жюри «а где реальный eGov?» —
с датами, механизмом и честными границами. Продуктовое решение: основная кнопка входа для гражданина — «Войти через
eGov mobile», ИИН — идентификатор гражданина; пока адрес сервиса eGov mobile (Smart Bridge) не предоставлен, кнопка остаётся
на месте, честно говорит «вход через eGov недоступен — войдите по логину и паролю» и никакого входа не имитирует.

## 1. Как гражданин входит в государственные сервисы сегодня

- **eGov mobile**: ЭЦП выпускается в приложении (ИИН + SMS + видеопроверка), далее код быстрого доступа или Face ID;
  с 2022 года вход только через биометрию Digital ID [egov.kz/cms/ru/articles/Android-IOS, 28.04.2026;
  informburo.kz, 20.07.2022].
- **egov.kz**: eGov QR (скан из приложения), ЭЦП + SMS, ИИН + пароль с подтверждением ЭЦП [nitec.kz, 24.11.2025];
  eGov 3.0 — QR или ЭЦП + код из приложения [zakon.kz, 11.08.2026].
- **Медицина в eGov mobile** уже есть: 22 услуги раздела «Здравоохранение», включая «Выдача направления пациентам на
  госпитализацию в стационар», выписки из карты стационарного больного, раздел eDensaulyq с фактами госпитализации и
  лабораторными результатами [egov.kz/cms/ru/categories/health_care, 22.09.2026; tengrinews.kz, 24.03.2023];
  с 31.08.2026 — «доверенные контакты» при госпитализации, до 3 человек по ИИН, согласие SMS-кодом [nitec.kz, 31.08.2026].
- **Портал бюро госпитализации**: пациент смотрит лист ожидания «по коду из талона или ИИН»
  [egov.kz/cms/ru/articles/health_care/2Fportal_byro_gosp, 25.04.2025; almatyzdrav.kz].

Вывод для продукта: ИИН — ключ поиска, но нигде не фактор входа; везде рядом ЭЦП, SMS или биометрия.

## 2. Вход во внешнее приложение через eGov mobile

- **Публичного OIDC «Sign in with eGov» нет.** `idp.egov.kz` показывает «Login with OAuth 2.0» без документации для
  третьих сторон — не подтверждено.
- **Официальный механизм** — «QR-подписание посредством eGov mobile» через Smart Bridge, паспорт сервиса NITEC-S-5096,
  для «информационных систем государственных и негосударственных органов» [pki.gov.kz, 07.10.2022]. Схема: бэкенд формирует
  одноразовый URL и QR, пользователь сканирует его в eGov mobile и подписывает ЭЦП, подпись с сертификатом (в нём ИИН)
  возвращается в систему [habr.com/ru/articles/711388, 18.01.2023]. Так входят ИС ЭСФ КГД [pro1c.kz, 10.04.2024] и
  частный idocs [idocs.kz].
- **Предпосылки**: заявка в НИТ, тестовая и продуктивная среды, сертификаты ШЭП, mTLS [t.me/s/sb_shep]; согласование
  теста до 2 рабочих дней по проекту приказа [uchet.kz, 16.09.2025]; оценка вендоров — 5–15 рабочих дней плюс аудит ИБ
  [osn.kz, 31.03.2026]. Тестовые ИИН и публичный sandbox eGov mobile не найдены — не подтверждено.
- **Сторонний мост**: SIGEX заявляет QR-подписание через eGov mobile без регистрации в Smart Bridge и аутентификацию по
  цифровым сертификатам [sigex.kz/blog/2022-12-14-signing-via-qr, 14.12.2022]. Продакшн-путь всё равно Smart Bridge.

## 3. Что сделано в Darumen

| Что | Состояние |
|---|---|
| Кнопка «Войти через eGov mobile» на экране входа мобилки и веба | доступность — из API: `GET /api/v1/public/service-status` → `egov.available` (конфиг `Services:Egov:Endpoint`; пуст — `reason: endpoint_not_provided`). Пока адрес сервиса eGov mobile (Smart Bridge) не предоставлен, кнопка остаётся, но вторичная, с подписью «Недоступно: адрес сервиса eGov mobile не предоставлен»; нажатие открывает пояснение «вход через eGov недоступен — войдите по логину и паролю» с кнопкой входа; то же пояснение — в `<details>` на странице входа Keycloak (`dmEgovSoon`). Никаких фальшивых QR и «успешных» входов. Когда адрес задан — вход через брокер realm (`kc_idp_hint=egov`). Веб — без флага сборки (`VITE_EGOV_ENABLED` удалён 28.09.2026); мобилка — по тому же контракту API |
| ИИН как идентификатор гражданина | клейм `iin` в Keycloak (маппер на клиентах `darumen-web`, `darumen-mobile`; у демо-пользователя `citizen1` значение синтетическое `000000000001`, невалидное по формату намеренно); API читает его в `CurrentUser.Iin`, маршрут гражданина сидируется от ИИН, иначе от учётной записи; ИИН не логируется (`Roles.Audited` без `citizen`) и не хранится |
| Показ ИИН в интерфейсе | только маской `•••••••• 0001`; ввод ИИН руками не делаем — без eGov-авторизации это сбор персональных данных без необходимости (§10.2 ТЗ) |
| Логин и пароль (Keycloak) | рабочий вход для стенда: `citizen1`, `doctor1` |
| Без входа | только экран входа (с 27.09.2026); памятка пациенту по QR — публичная |

## 4. Что запрошено и что дальше

1. Через организаторов (НИТ — data-партнёр хакатона) — заявка на тестовый контур Smart Bridge для QR-подписания
   (NITEC-S-5096). До ответа: заглушка. На защите показываем заявку и схему.
2. Трек «если возможно»: один день на проверку SIGEX на стенде (подписать challenge → получить сертификат → извлечь ИИН).
   Если работает — включаем за флагом с отдельным экраном согласия (перечень данных: ИИН, ФИО из сертификата; ИИН
   хранится только хешем — требование закона № 326-VIII от 24.06.2026 об идентификаторах персональных данных) и
   подписываем как «сторонний мост». Если не подтверждается за день — остаётся заглушка.
3. Roadmap, подписанный явно в профиле и на слайде: вход через eGov mobile (Smart Bridge); чтение направления и фактов
   госпитализации из ЕИСЗ через eGov (услуга и раздел eDensaulyq уже существуют); доверенные контакты при госпитализации;
   push через eGov mobile; доступ за членов семьи.

## 5. Персональные данные

- Закон РК «О персональных данных и их защите» (№ 94-V): сбор и обработка — с согласия субъекта (ст. 7), согласие через
  государственный сервис контроля доступа для данных госсистем (ст. 8) [adilet.zan.kz/rus/docs/Z1300000094].
- Закон № 326-VIII от 24.06.2026: ИИН, ФИО, изображение лица — идентификаторы персональных данных; при хранении —
  маскирование и хеширование; медицинские данные повышают категорию оператора [digitalbusiness.kz, 28.06.2026].
- Следствия для Darumen: стенд не хранит персональных данных (маршруты синтетические), ИИН показывается маской и
  используется только как сид, согласие при реальной интеграции — отдельный непроставленный чекбокс с перечнем данных.
